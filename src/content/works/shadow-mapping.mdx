## Shadow Mapping: From Light to Visibility

> 把"光线是否被挡住"压缩成一次纹理深度比较

光线追踪问"这个像素看到什么"。Shadow Mapping 解决一个更具体的问题：**"光源能不能看到这个着色点"**。把这个问题离线烘焙成一张深度图，运行时就只剩一次纹理读取 + 一次比较。

下面这个交互场景把整张图压在一起：拖动光源、调整 shadow map 分辨率与 bias，立即看到阴影质量随之变化。

## 01 / 阴影到底在算什么？

> **核心问题：** 阴影在渲染方程里对应哪一项？

直接光照的着色公式中，可见性 $V(x, \omega)$ 是一个二值函数：

$$
L_o(x, \omega_o) = \int L_i \cdot \rho \cdot (n \cdot \omega_i) \cdot V(x, \omega_i) \, d\omega_i
$$

阴影 = $V(x, \omega_i) = 0$ 的区域。如果对每个 fragment 朝光源射一条 ray 求 $V$，渲染会非常昂贵。**Shadow Mapping 把这个查询变成一次纹理读取**：把光源到场景的"最近表面深度"提前烘焙成纹理，运行时只比较深度。

<VisibilityFunctionExplainer client:only="react" />

> 💡 **小结：** Shadow map 不存阴影，它存"光源能看到的最近深度"。阴影是运行时 **比较** 出来的。

**自测：** 一张 shadow map 实际存的是 (a) 颜色 (b) 阴影掩码 (c) 深度 (d) 法线？

## 02 / Two-Pass Rendering 流程

> **核心问题：** 为什么 Shadow Mapping 必须分两遍？

**Pass 1**：把"相机"换到光源位置 + 朝向，渲染整个场景，**只写入深度缓冲**。结果作为纹理保存 → Shadow Map。

**Pass 2**：从真正的相机视角渲染。对每个 fragment：把世界坐标变换到光源裁剪空间，得到 $(u, v, z)$。用 $(u, v)$ 采样 shadow map 拿到 `closestDepth`，比较 `z` 是否更远。

下面同时展示两个 pass 的视角：左是光源看见的轮廓（决定 depth map），右是相机看到的最终阴影。请让"左侧背向光的区域"和"右侧的阴影区域"对应起来。

<TwoPassPlayground3D client:only="react" />

> 💡 **小结：** Pass 1 写深度，Pass 2 读深度。这两遍的中间产物就是 Shadow Map。

**自测：** 一个物体只在 Pass 2 出现，没有在 Pass 1 渲染过，它会投射阴影吗？

## 03 / Light-Space Transform

> **核心问题：** 相机看到的 fragment，怎么知道自己在 Shadow Map 上对应哪个 texel？

矩阵链：

$$
\mathbf{p}_{\text{clip}}^{\text{light}} = P_{\text{light}} \cdot V_{\text{light}} \cdot \mathbf{p}_{\text{world}}
$$

**透视除法 → NDC：**

$$
\mathbf{p}_{\text{ndc}} = \frac{\mathbf{p}_{\text{clip}}.xyz}{\mathbf{p}_{\text{clip}}.w}
$$

**映射到 Shadow Map UV：**

$$
u = 0.5 \cdot x_{\text{ndc}} + 0.5, \quad v = 0.5 \cdot y_{\text{ndc}} + 0.5
$$

$$
z_{\text{shadow}} = 0.5 \cdot z_{\text{ndc}} + 0.5
$$

如果 $u \notin [0, 1]$ 或 $v \notin [0, 1]$，说明 fragment 跑出了 light frustum，shadow map 没有对应数据 —— 通常会按"lit"或"shadow"来 fallback。

<LightSpaceTransformLab client:only="react" />

> 💡 **小结：** Light-Space Transform 是 Pass 1 和 Pass 2 之间的**桥梁**。fragment 必须"重新站到光源位置"才能查到自己的可见性。

**自测：** fragment 投影到 shadow map 之外通常说明什么？应该被处理为 lit 还是 shadow？

## 04 / Shadow Test：一次比较

> **核心问题：** 怎么用一次深度比较判断阴影？

$$
\text{currentDepth} = z_{\text{fragment}}^{\text{light}}
$$

$$
\text{closestDepth} = \text{shadowMap}(u, v)
$$

$$
\text{inShadow} = (\text{currentDepth} - \text{bias}) > \text{closestDepth}
$$

GLSL 伪代码：

```glsl
vec4 lightClip = lightVP * vec4(worldPos, 1.0);
vec3 ndc = lightClip.xyz / lightClip.w;
ndc = ndc * 0.5 + 0.5;                     // [-1,1] → [0,1]
float currentDepth = ndc.z;
float closestDepth = texture(shadowMap, ndc.xy).r;
float shadow = (currentDepth - bias) > closestDepth ? 1.0 : 0.0;
```

下面这个组件把比较过程拉到一根坐标轴上，可以拖动 fragment 和 occluder 的位置：

<ShadowDepthComparisonLab client:only="react" />

> 💡 **小结：** Shadow Test 本身只是减法 + 比较；难点在前面的坐标变换和 bias。

**自测：** 如果 currentDepth = 0.4，closestDepth = 0.6，bias = 0.005，结果是 lit 还是 shadow？

## 05 / Shadow Acne 是怎么来的？

> **核心问题：** 物体凭空给自己投下斑驳阴影，到底是哪里出问题了？

Shadow Map 是一张**离散**的纹理：

- 每个 texel 在世界空间覆盖一段区域
- 这一片区域里，shadow map 只能存**一个**深度值（最近的那个）
- 真实表面是连续倾斜的，但 shadow map 是阶梯式的
- 同一片表面上，多数点的 currentDepth 比 texel 记的 closestDepth 略大 → 误判为自我遮挡

<AcneGeometryExplainer client:only="react" />

直观演示：开启不同 bias 看实际场景：

<ShadowAcneBiasLab client:only="react" />

> 💡 **小结：** Acne 不是 bug，是 shadow map 离散化 + 浮点精度的副作用。Bias 的本质是把 currentDepth 朝光源方向"挪一点点"，让它逃出 texel 的量化误差。

**自测：** 同一个 shadow map 分辨率下，平面越斜（normal 越偏离光线）acne 会更严重还是更轻微？

## 06 / Bias、Peter Panning 与 Slope-Scale

> **核心问题：** Bias 不是越大越好。怎么平衡？

- **bias 太小** → shadow acne。
- **bias 太大** → 阴影"漂浮"，从物体底部开始就脱离物体本身（**Peter Panning**）。
- **slope-scale bias**：bias 随表面与光线夹角变化 —— 越斜越大。
- **normal bias**：把比较点沿表面法线方向推一小段，几何上避免 acne 而不是改 z。

## 07 / Resolution × Light Frustum = 阴影质量

> **核心问题：** 为什么把 shadow map 调到 2048×2048 还是糊？

阴影的"清晰度"由 **一个 texel 在世界空间的尺寸**决定：

$$
\text{world texel size} \approx \frac{\text{light frustum width}}{\text{shadow map resolution}}
$$

也就是说：

- 提高 resolution 让 texel 更小。
- 收紧 light frustum 也能让 texel 更小（同样分辨率，覆盖更小的世界范围）。
- 两个一起调最有效。

<ShadowResolutionAliasingDemo client:only="react" />

> 💡 **小结：** "1024² 不够清晰"通常意味着 **frustum 太大** ，而不是分辨率本身的问题。

**自测：** 把 shadow map 从 1024² 调到 2048²，但同时把 frustum 范围也翻倍，texel 世界尺寸会怎么变化？

## 08 / PCF：让边缘不那么硬

> **核心问题：** 怎么把锯齿边缘变成柔和过渡？

PCF（Percentage-Closer Filtering）的关键不是过滤深度，而是**过滤比较结果**：

```glsl
float shadow = 0.0;
for (int y = -h; y <= h; y++)
  for (int x = -h; x <= h; x++) {
    float closest = texture(shadowMap, uv + vec2(x, y) * texel).r;
    shadow += (currentDepth - bias) > closest ? 1.0 : 0.0;
  }
shadow /= float((2*h+1) * (2*h+1));
```

每个邻居 texel 单独做一次 shadow test，结果取平均。kernel 越大，软化程度越高，但成本随 $k^2$ 增长。

<PCFFilteringDemo client:only="react" />

> 💡 **小结：** PCF 是过滤"比较结果"。直接对深度图做模糊得到的是错的（深度不能线性插值得到正确的 visibility）。

**自测：** 3×3 PCF 和 7×7 PCF 哪个更柔？哪个 GPU 成本更高？

## 09 / PCF 的极限：不是物理软阴影

> **核心问题：** 真实软阴影是怎么形成的？PCF 为什么不是？

真实软阴影来自**面积光源**：光源有面积 → 接收点的某些方向被遮挡某些没被 → 产生半影 (penumbra)。直觉公式：

$$
w_{\text{penumbra}} \propto \frac{d_{\text{receiver}} - d_{\text{blocker}}}{d_{\text{blocker}}} \cdot w_{\text{light}}
$$

也就是 blocker 离 receiver 越远，半影越宽；离得越近，阴影越锐。

PCF 用的是**固定 kernel**，软化程度跟 blocker 距离没关系。**PCSS** 在 PCF 前加一步 blocker search，根据估算的 blocker 距离动态调整 kernel 大小，从而模拟出"近锐远柔"的效果。

<PCSSPenumbraLab client:only="react" />

> 💡 **小结：** PCF 是工程近似，不区分位置；PCSS 用统计方法把 blocker 距离引入 kernel 大小，更接近物理真实。

**自测：** blocker 紧贴 receiver（如球体踩在地面上）时，半影应该是宽还是窄？PCF 能否表现这一点？

## 11 / Cascaded Shadow Maps · 大场景方向光的标配

> **核心问题：** 为什么 1024² 的 shadow map 在开放世界中不够？

单张 shadow map 既要覆盖近处（要看清角色脚下细节），又要覆盖远处（几公里外），分辨率根本不够分。**CSM** 把相机视锥按距离切几段，每段一张专属 shadow map：

- Cascade 0：0–10m，最高精度
- Cascade 1：10–30m
- Cascade 2：30–100m
- Cascade 3：100–500m

近处 cascade 的 frustum 小、texel 小、阴影锐；远处 cascade 反之。

<CascadedShadowMapsLab client:only="react" />

> 💡 **小结：** CSM 把"精度"作为可调参数沿距离分配。几乎所有 3A 游戏的太阳阴影都用 CSM。

**自测：** 角色在玩家身边时，应该用哪一个 cascade？为什么 split 通常不是均匀分布？

## 12 / 调试套路：Symptom → Cause → Fix

> **核心问题：** 实际项目中阴影出问题，从哪里下手？

参见上面 Section 06 的 checklist。最有用的两个调试技巧：

1. **可视化 light frustum**：用 `cameraHelper` 直接画出来，确认覆盖范围。
2. **把 shadow map 渲到屏幕角落**：作为 debug overlay，立刻看出深度分布是否正确。

辅助招式：临时把 bias 设成 0（看 acne 的真实分布），临时关闭 PCF（看真实边界），临时只渲染深度（确认 light view 正确）。

> 💡 **小结：** Shadow Mapping 是参数堆得很深的算法，可视化中间结果是降低 debug 成本最有效的方式。

**自测：** 如果阴影完全没出现，你最先检查的 3 件事是什么？

## 13 / 阴影技术族谱

> **核心问题：** Hard / PCF / PCSS / VSM / Ray Traced 各自的位置在哪？

<ShadowTechniquesComparison client:only="react" />

简版：

| 技术 | 软阴影 | 物理近似 | 相对成本 | 典型用途 |
|------|--------|----------|----------|----------|
| Hard | ✗ | ✗ | 1× | 风格化 / 极限性能 |
| PCF | ✓ | ✗ | k²× | 实时项目默认 |
| PCSS | ✓ | 近似 | ~2× PCF | 中高端实时 |
| VSM | ✓ | 近似 | hard + mip | 角色阴影 / 远景 |
| Ray Traced | ✓ | ✓ | 高 | RTX、离线 |

> 💡 **小结：** 工程上的演进路线大致就是 hard → PCF → PCSS → ray traced。VSM 是一条用统计学绕开离散化的支线。

## 14 / 总结：从 Light Pass 到 Soft Shadow

<ShadowMappingSummaryMap client:only="react" />

整页主线：

> **light → depth map → light-space transform → depth compare → visibility**

### 核心公式速查

| 主题 | 公式 |
| --- | --- |
| Visibility | $V(x, \omega) \in \{0, 1\}$ |
| Light-space | $\mathbf{p}_{\text{ndc}} = (P_{\text{light}} V_{\text{light}} \mathbf{p}_{\text{world}}) / w$ |
| UV mapping | $u = 0.5 x_{\text{ndc}} + 0.5$ |
| Shadow test | $(\text{currentDepth} - \text{bias}) > \text{closestDepth}$ |
| Texel size | $\text{frustum} / \text{resolution}$ |
| PCF | $\frac{1}{k^2} \sum_{i,j} \mathbb{1}[(z - b) > z_{ij}]$ |
| PCSS penumbra | $w \propto (d_r - d_b)/d_b \cdot w_{\text{light}}$ |

### 关键直觉提醒

- Shadow map 存的是**深度**，不是阴影。
- 阴影由 Pass 2 的 **比较** 决定。
- Acne / peter panning / aliasing 都是同一个底层问题（深度离散化）的不同症状。
- **Bias** 解决 acne，但带来 peter panning。
- 阴影清晰度 = $\text{frustum} / \text{resolution}$，两个一起决定。
- **PCF** 过滤的是 shadow test 结果，不是深度。
- **PCSS** 是 PCF + blocker search，半影宽度跟随 blocker 距离。
- **CSM** 是大场景方向光的事实标准。
